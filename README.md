# ГеоКрио ГИС (GeoCrio GIS)

Веб-ГИС + мобильное PWA для геоинформационного обеспечения района учебных
полевых практик и геокриологического полигона. Полное ТЗ — см. `docs/`.

## Статус

- **Этап 0 (схема БД)** — готов и проверен запуском на локальном Postgres 16
  + PostGIS 3 (регистрация → автосоздание профиля, RLS по ролям, триггер
  "точка вне полигона", запрет самоповышения роли, аудит insert/update/
  delete/restore). Подробности и найденные при этом баги — в
  `docs/schema-review.md`.
- **Этап 1 (каркас Next.js + Auth)** — готов. Next.js `16.3.4` + React
  `19.2.8` (текущие стабильные версии на момент разработки — не Next 14,
  как в исходном тексте ТЗ: раздел 2 писался до выхода Next 15/16, а более
  старая линия 14.x больше не получает патчей безопасности, см. ниже).
  Собирается и линтится без ошибок и предупреждений (`npm run build`,
  `npm run lint`, `npx tsc --noEmit`), юнит-тесты гейтинга проходят
  (`npm test`). Проверено вручную через `next dev`: главная страница
  редиректит на `/map`, защищённые маршруты без сессии уводят на `/login`
  с сохранением `redirectTo`, `/admin/*` физически недостижим без роли
  admin, форма логина/регистрации рендерится, open-redirect через
  `redirectTo` заблокирован. Реальный вход/регистрация против живого
  Supabase не проверялись — нет проекта/ключей в среде разработки (см.
  раздел «Проверить при первом деплое» ниже).
- **Этап 2 (карта + CRUD скважин/точек)** — готов. MapLibre GL JS 6 поверх
  OSM-тайлов, штриховая граница активного полигона, кластеризация
  скважин/точек по цветам ТЗ (`#D85A30` / `#534AB7`), клик по маркеру →
  попап с профилем + кнопки «Профиль»/«Редактировать», клик по свободной
  карте → правая панель добавления объекта. Панель слоёв, статистика
  полигона, поиск по коду, координаты курсора. CRUD через Server Actions
  с автопривязкой `created_by = auth.uid()` под RLS, soft delete через
  `is_deleted`. Профили `/boreholes/[id]` и `/observation-points/[id]` +
  `/edit`-страницы.
- **Этап 2.5 (полноценная платформа: пользовательские участки + команды)**
  — готов. Приложение перешло от «один зашитый seed-полигон» к
  многопользовательской модели. Любой геолог заводит свои **участки**
  (полигоны): рисует границу кликами на карте (terra-draw), или
  загружает из файла GeoJSON/KML/GPX (`@tmcw/togeojson`). Участок по
  умолчанию **приватный**, виден только автору и приглашённым
  соавторам. Владелец может **пригласить соавторов по email** (RPC
  `invite_polygon_member`), опубликовать участок галочкой `is_public`
  (тогда все зарегистрированные геологи видят его read-only), или
  удалить. Селектор активного участка в шапке, URL-паттерн
  `?polygon=<id>` для шеринга. На карточках объектов виден автор,
  дата создания и изменения; кнопки редактирования скрыты для
  пользователей вне команды участка. RLS-политики на все аудируемые
  таблицы (`boreholes`, `observation_points`, `measurements`, `photos`,
  `field_notes`) переписаны через helper-функции `fn_can_read_polygon` /
  `fn_can_write_polygon` — единая точка правды. Роли `researcher`/
  `student` в БД остались для совместимости, но в UI объединены в одно
  состояние «Геолог». Мобильная навигация зачищена от заглушек. Прогнано
  на локальном Postgres+PostGIS: полный сценарий «Иванов создал приватный
  полигон → пригласил Петрова → тот добавил скважину → опубликовали →
  Сидоров видит, но не может править» — все шаги проходят RLS корректно.

Все запланированные этапы (0…6) реализованы. Ниже — дорожная карта
с деталями каждого; она пересобрана по итогам продуктового аудита и
разведки реальных ГИС-платформ (iNaturalist, GTN-P, QFieldCloud,
Mergin, Fulcrum, ODK, OSM, Wikipedia).

## Этапы разработки

Порядок выбран так, чтобы каждый этап был проверяемым сам по себе и не
блокировался незавершённостью следующего.

- **Этап 0 — Схема БД (готово)**
  `supabase/migrations/001_initial_schema.sql`, `002_storage_setup.sql`.
  Таблицы, RLS, триггеры (аудит, автосоздание профиля, запрет самоповышения
  роли), views, Storage-политики. См. `docs/schema-review.md` — что было
  исправлено относительно исходного ТЗ.

- **Этап 1 — Каркас Next.js + Auth (готово)**
  Next.js 16 (App Router) + Tailwind CSS 3, Supabase client/server через
  `@supabase/ssr`, страницы `login`/`register` (Server Actions,
  `useActionState`), чтение роли из `profiles` (`getCurrentProfile`),
  защищённый layout `(main)` с тёмной шапкой/навигацией/мобильным нижним
  меню (раздел 12 ТЗ), `proxy.ts` (бывший `middleware.ts`, см. ниже) для
  гейтинга сессии, `/admin/*` — отдельный server-side гейт по роли.
  Разделы `/map`, `/data`, `/analytics`, `/export`, `/admin/*` — заглушки
  до соответствующих этапов.

- **Этап 2 — Карта + CRUD скважин/точек наблюдений (готово)**
- **Этап 2.5 — Полноценная платформа: пользовательские участки + команды
  (готово)**
  Миграция `004_multi_user_polygons.sql`, компоненты рисования полигонов
  (terra-draw), импорт GeoJSON/KML/GPX, страницы `/polygons/*`, RPC
  приглашения соавторов.

- **Этап 3.1 — Полевая работа онлайн (готово)**
  Кнопка «Взять моё GPS-местоположение» с индикатором точности (accuracy
  в метрах), автозамена запятой на точку в координатах, мобильный UX
  карты (bottom-sheet для формы добавления, явный FAB `+` вместо
  случайного клика), загрузка фото со сжатием на клиенте (canvas → 1200
  px + thumbnail 300 px) и извлечением GPS из EXIF, экспорт CSV
  (с BOM для Excel) и GeoJSON (для QGIS/ArcGIS) через
  `/api/export?polygon=<id>&format=…`, Realtime-подписка на изменения
  boreholes/observation_points с троттлингом.

- **Этап 3.2a — PWA + офлайн-каркас (готово)**
  Приложение теперь устанавливается на главный экран телефона (`app/
  manifest.ts` + иконки 192/512/maskable/apple-touch, `theme_color`,
  `display: standalone`, `start_url: /map`). Собственный Service Worker
  (`public/sw.js`) кэширует статику Next.js (`/_next/static/*`) и **плитки
  OSM** — cache-first с мягким LRU на 800 плиток (~2 областей карты в
  разных масштабах). Значит: геолог открыл нужный район с интернетом —
  завтра в поле без сети та же область покажется. Включён
  `experimental.useOffline` из Next 16: при пропаже связи навигации, RSC-
  запросы и Server Actions не падают, а держатся pending и автоматически
  повторяются, когда сеть вернётся. Баннер `OfflineBanner` в шапке
  сообщает статус, `InstallPrompt` — подсказка iOS/Android для установки.

- **Этап 3.2b — Полный офлайн для форм (готово)**
  IndexedDB (через `idb`) как очередь мутаций. Формы скважины/точки и
  загрузчик фото при отсутствии связи не роняются, а кладут операцию в
  локальную очередь (`lib/offline/db.ts` + `lib/offline/queue.ts`) и
  сразу редиректят на карту — с текстом «сохранится, когда сеть
  вернётся». В шапке — индикатор `SyncStatus` с числом ожидающих
  операций; клик по нему запускает `drain()` вручную. Автодрейн: при
  монтировании, на событие `online`, каждые 60 секунд как страховка.
  Server Actions вызываются напрямую из клиента через
  `*FromQueue`-обёртки без `redirect()` (обычные `redirect`-версии
  оставлены для онлайн-формы, чтобы работать через `useActionState`).

- **Этап 3.3 — Кэш чтения (опциональный, отложен)**
  Кэш прочитанных скважин/точек/полигонов в IDB, чтобы `/data` и профили
  открывались офлайн. Пока это лишь app shell + плитки; сами объекты
  требуют сеть.

- **Этап 4 — Замеры температуры и мерзлота (готово)**
  Ядро геокриологии. **Раскраска маркеров на карте** по статусу
  мерзлоты (переключатель в LayerPanel: «Тип объекта» ↔ «Статус
  мерзлоты»), цвета — красный (мёрзлый, t &lt; −0,5), синий
  (переходный, −0,5…+0,5), оранжевый (талый, t &gt; +0,5), серый (нет
  замеров). Легенда в панели адаптируется под режим. **CRUD замеров
  температуры** — таблица `measurements` из БД теперь работает
  из UI: форма ввода в профиле скважины (глубина, температура, дата с
  автозаполнением «сейчас», заметки), таблица всех замеров с плашками
  по интерпретации, мягкое удаление. **График T(z)** — inline SVG без
  библиотек, ось глубины инвертирована (0 сверху), вертикальная
  пунктирная линия T=0 °C — граница фазового перехода; «человеческие»
  тики по осям (D3-nice), hover-подсказки на точках. Профиль скважины показывает
  вычисленный статус мерзлоты + последний замер сверху.

- **Этап 5.1 + 5.2 — Доверие к данным: базовое (готово)**
  Toast-система (`components/ui/Toast.tsx`) без библиотек — контекст +
  провайдер в root layout, `useToast()` возвращает `showToast({kind,
  message})`. Модальный `ConfirmDialog` заменил `window.confirm` в
  `SoftDeleteButton` и `MeasurementList` — теперь модалка мобильна,
  с кодом объекта в заголовке («Удалить скважину Скв-01?»), Esc и клик
  по фону = отмена. Замеры удаляются через `ConfirmDialog` + toast с
  переходом «восстановить можно в Корзине».

  **Корзина** (`/trash`): свои удалённые скважины, точки и замеры,
  кнопка «Восстановить» снимает флаг `is_deleted`, объект возвращается
  на карту и в списки. Ссылка на корзину — на странице `/data`. Server
  Actions `restore*Action` перешли на возврат `{ok, error?}` — унифицировано
  с queue-friendly версиями.

  **История изменений** — секция «История» на профилях скважины и
  точки. Читает audit_log через новую RPC `fn_object_history` (миграция
  `005_object_history_rpc.sql`) — `SECURITY DEFINER` + `SET search_path
  = public`, проверяет право чтения через `fn_can_read_polygon`.
  Diff показывает только реально изменившиеся поля (before → after),
  бейджи по типу действия (создание/изменение/удаление/восстановление).
  Проверено на локальном Postgres+PostGIS: функция создалась, отдаёт
  пусто без права чтения, падает с понятной ошибкой на неподдерживаемой
  таблице.

- **Этап 5.3 — Предложения правок (готово)**
  Модель iNaturalist Community Taxon: любой авторизованный геолог,
  видя чужую скважину или точку, жмёт «Предложить правку», заполняет
  форму (какие поля менять и зачем). Через предложения меняются
  только «безобидные» поля — код, глубина, тип грунта/точки, описание;
  **координаты через proposals не редактируются** — существенное
  изменение геометрии остаётся привилегией автора (иначе пять
  человек сговорились бы сдвинуть чужую скважину на 200 м).
  Автор объекта (или админ) видит вход в «Мои уведомления» (`/inbox`)
  и решает: «Принять» или «Отклонить» с комментарием. **Порог
  сообщества**: если ≥3 других геолога (не автор объекта, не автор
  предложения — RLS это гарантирует) отметили «+1 согласен» —
  правка применяется автоматически триггером БД. Автор предложения
  может «Отозвать» в любой момент до решения.

  Миграция `006_edit_proposals.sql` создала таблицы `edit_proposals`
  и `edit_proposal_votes`, три SECURITY DEFINER RPC
  (`fn_apply_edit_proposal` — единая точка применения; `fn_reject`,
  `fn_withdraw`), триггер `fn_check_proposal_threshold` на INSERT
  голоса, полный RLS и явные GRANT для роли authenticated (иначе
  self-hosted постгрес отказал бы). Прогнано на локальном
  Postgres 16+PostGIS: все 7 сценариев (автор пытается своё → RLS
  fail; автор объекта пытается голосовать → RLS fail; 3-й голос →
  auto-apply + boreholes.code обновлён; и т.д.) проходят как
  задумано.

  UI: `ProposeEditForm` (кнопка + разворачивающаяся форма только для
  тех, кто не автор объекта), `ProposalList`+`ProposalCard` в
  профиле объекта — три ветки действий (автор объекта — «Принять/
  Отклонить», автор предложения — «Отозвать», остальные — «+1» /
  «убрать голос»), `ConfirmDialog` с полем комментария на отклонение,
  toast на каждое действие. Страница `/inbox` — две секции:
  «Входящие» (чужие пропозалы по моим объектам, ждут моего решения) и
  «Исходящие» (мои пропозалы, ждут решения). Ссылка «Уведомления»
  добавлена в верхнюю навигацию.

- **Этап 6 — Полировка и админка (готово)**
  Глобальный errorMap для zod (`lib/zod-ru.ts`) — все стандартные
  сообщения на русском: «Обязательное поле» вместо «Required»,
  «Допустимые значения: „a“, „b“» вместо «Invalid enum value»,
  «Минимум N символ(ов)», «Введите корректный email/URL» и т.д.
  Проверено смок-запусками. Наши явные `message` во всех схемах
  побеждают default — тексты, где они есть, не изменились.

  **Аналитика по участку** (`/analytics?polygon=<id>`, редирект как
  у `/data`): 4 stat-tile'а (скважины, точки, всего замеров, средняя
  t° последних замеров), горизонтальный bar chart распределения
  скважин по статусу мерзлоты (frozen/transitional/thawed/unknown с
  цветами палитры), гистограмма замеров за 30 дней (inline SVG, без
  библиотек, hover-подсказки).

  **Админ-панель**: `/admin/users` показывает всех пользователей
  платформы (ФИО, роль, свои участки, состоит-в-команде, дата
  регистрации). `/admin/audit` — 200 свежих записей из audit_log
  (RLS `al_read USING (is_admin())` защищает от чтения не-админом),
  с ФИО пользователя и человеческим названием таблицы/действия.
  Управление ролями пока через SQL Editor (в UI не добавлено —
  чтобы не сделать случайно «админ-выстрел в ногу»; отдельный шаг).

- **Security hardening (миграция 007)** — по итогам полного аудита:
  * Закрыта **HIGH-уязвимость** в edit_proposals: подмена `polygon_id`
    в INSERT позволяла атакующему создать пропозал на чужую скважину
    в чужом приватном полигоне (target из закрытого X, polygon_id из
    своего публичного Y), собрать 3 голоса от подельников и применить
    правку через триггер (обход RLS `ep_read`). Политика `ep_insert` +
    `epv_insert` теперь требуют совпадения `polygon_id` с реальным
    polygon'ом target'а; `fn_apply_edit_proposal` дополнительно
    проверяет то же в WHERE (defense in depth). Регресс-тест на
    локальной БД проходит: подмена → RLS FAIL.
  * Валидация `proposed_data` на сервере через CHECK-триггер: раньше
    некастуемый `depth_m: "abc"` попадал в БД и клал триггер
    auto-apply. Теперь падает раньше, на INSERT.
  * `fn_audit_changes.user_id` теперь берётся с приоритетом из
    `auth.uid()` (реальный субъект действия), а не из
    `created_by/measured_by/uploaded_by` записи. В истории видно,
    кто именно внёс изменение — важно для accepted proposals и
    admin-действий.
  * `deletePhotoAction`: явная проверка `auth.getUser()`, порядок
    операций теперь безопасный (сначала DB DELETE через RLS, только
    потом Storage remove — исключает «висячие» файлы или строки).
    Возврат `{ok, error}` вместо throw, `PhotoGallery` использует
    `ConfirmDialog` + toast вместо `window.confirm`.

## Отступление от версии в ТЗ: Next.js 16 вместо Next.js 14

Раздел 2 ТЗ называет Next.js 14 — на момент его написания это была текущая
версия. К моменту разработки Next.js 14.x (последняя патч-версия —
`14.2.35`) вышел из активной поддержки и содержит минимум 5 непропатченных
high-severity уязвимостей (DoS, cache poisoning, request smuggling и др. —
`npm audit`), патч для части которых есть только начиная с `15.5.16`/
`16.2.5`. Приложение будет обрабатывать реальную аутентификацию
пользователей — сознательно оставлять известные дыры ради буквального
соответствия номеру версии в документе, написанном до выхода Next 15/16,
было бы неправильным решением. Взята текущая стабильная `16.3.4` (React
`19.2.8` — Next 16 всё ещё поддерживает React 18, но `useFormState`
(react-dom) заменён на стабильный `useActionState` из React 19, поэтому
согласованная пара — React 19).

Практическое следствие для тех, кто продолжит разработку (в т.ч. для
ИИ-агентов, тренированных на более старых версиях Next.js): часть
паттернов Next 14 в этом проекте не работает.
- `cookies()`/`headers()` из `next/headers` — асинхронные (`await`
  обязателен).
- `searchParams`/`params` в Page/Layout — `Promise`, а не обычный объект.
- Файл `middleware.ts` переименован в `proxy.ts` (экспортируемая функция —
  `proxy`, а не `middleware`; остальной API идентичен).
- Формы на Server Actions используют `useActionState` из `'react'`, а не
  `useFormState` из `'react-dom'` (последний в React 19 отсутствует).

При каждом `next dev` Next.js сам генерирует/обновляет `AGENTS.md` (и
`CLAUDE.md`, ссылающийся на него) с предупреждением именно об этом —
файл специально коммитится в репозиторий, не добавляйте его в
`.gitignore`.

## Заменить тестовый полигон на реальный

`003_seed_polygon.sql` создаёт один тестовый полигон в районе Тюмени
(центр примерно 65.6°E, 57.2°N, 2×4 км). Чтобы поставить настоящий
полигон учебных практик ТИУ:

- **Вариант 1 — подправить миграцию до первого прогона**:
  заменить координаты в `POLYGON((...))` в `003_seed_polygon.sql`
  (WGS84 / EPSG:4326, порядок точек против часовой стрелки, первая = последней).
- **Вариант 2 — после появления админки в Этапе 6**: изменить границу
  через `/admin/polygons` в UI.
- **Вариант 3 — прямо сейчас через Supabase SQL Editor**:
  ```sql
  UPDATE polygons
     SET boundary = ST_GeomFromText('POLYGON((lng1 lat1, lng2 lat2, ..., lng1 lat1))', 4326),
         name = 'Учебный полигон ТИУ',
         default_zoom = 15
   WHERE id = '00000000-0000-0000-0000-000000000001';
  ```
