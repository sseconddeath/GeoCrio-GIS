# Ревью схемы БД (раздел 4 ТЗ + дополнение)

Проверка исходного ТЗ и присланного дополнения (3 правки: RLS `profiles`,
аудит `layers.uploaded_by`, Realtime). Ниже — что было принято как есть,
что доработано и почему. Всё уже внесено в
`supabase/migrations/001_initial_schema.sql` и `002_storage_setup.sql`.

## Правки из дополнения — приняты

1. RLS на `profiles` — добавлено, но потребовалась доработка (см. п.3 ниже).
2. Аудит `layers.uploaded_by` — добавлено, объединено с веткой `photos`
   (`WHEN TG_TABLE_NAME IN ('photos', 'layers') THEN (NEW).uploaded_by`).
3. Realtime — добавлена публикация `boreholes`, `observation_points`,
   `measurements` в `supabase_realtime`.

## Найдено дополнительно

### Критично

**1. Нет автосоздания `profiles` при регистрации.**
Ни в основном ТЗ, ни в дополнении нет триггера `auth.users → profiles`.
Без него после `supabase.auth.signUp()` строки в `profiles` просто не
существует, а вся ролевая модель (`is_admin()`, RLS-политики,
`created_by`/`measured_by`/`uploaded_by` со ссылкой на `profiles.id`)
на этом стоит.
→ Добавлен `fn_handle_new_user()` (`SECURITY DEFINER`) + триггер
`on_auth_user_created` на `auth.users`, роль по умолчанию — `student`.

**2. Аудит-триггер ломает все INSERT/UPDATE/DELETE на аудируемых таблицах.**
`audit_log` имеет RLS с единственной политикой — `SELECT` для админа.
INSERT-политики нет. `fn_audit_changes()` в исходном виде — обычная
(`INVOKER`) функция, значит её `INSERT INTO audit_log` выполняется от
имени вызывающей роли (обычного `researcher`/`student`), и RLS его
отклонит. То есть как только включаете RLS — падает любая операция на
`boreholes`, `measurements`, `observation_points`, `photos`,
`field_notes`, `layers`. Фикс дополнения (аудит `layers`) до этой ошибки
даже не доходит.
→ `fn_audit_changes()` объявлена `SECURITY DEFINER SET search_path =
public`. В Supabase миграции выполняются от `postgres`, который и есть
владелец `audit_log`, а владельцы таблиц по умолчанию не подпадают под
собственный RLS (если явно не включён `FORCE ROW LEVEL SECURITY`) — этим
и открывается путь для записи аудита без отдельной INSERT-политики.

**3. RLS-фикс `profiles` из дополнения не закрывает исходную уязвимость,
а маскирует её.**
`profiles_update_own USING (auth.uid() = id)` без `WITH CHECK`,
ограничивающего `role`, разрешает пользователю выполнить
`UPDATE profiles SET role = 'admin' WHERE id = auth.uid()` — RLS видит
только то, что он редактирует свою строку, полю `role` не важно, кто его
меняет. Именно то, от чего должна была защищать эта правка, остаётся
открытым для самого пользователя (а не только для чужих ролей).
→ Добавлен `fn_prevent_self_role_change()` (`SECURITY DEFINER`) +
`BEFORE UPDATE OF role ON profiles`, который проверяет `is_admin()` при
попытке сменить `role`. RLS-политики из дополнения оставлены как есть —
они всё ещё нужны для "остального" (имя, аватар).

### Найдено при реальном прогоне миграции (не видно при чтении кода)

Обе следующие ошибки проверены практически: поднят локальный Postgres 16 +
PostGIS 3, миграции накатаны, сценарии прогнаны под настоящими RLS-ролями
(`authenticated` + подмена `auth.uid()` через `request.jwt.claim.sub`).

**1а. `fn_audit_changes()` в исходной редакции ТЗ падает на первой же вставке
в `boreholes`.**
Конструкция `CASE WHEN TG_TABLE_NAME = 'measurements' THEN (NEW).measured_by
... END` обращается к полю композитного типа через `(NEW).field`. В
PL/pgSQL такое обращение резолвится на этапе разбора всего выражения, а не
лениво по выбранной ветке `CASE` — то есть если хотя бы в одной ветке
упомянуто поле, которого нет у фактического типа `NEW` (для `boreholes`
это `measured_by` и `uploaded_by`), функция падает с ошибкой `column
"measured_by" not found in data type boreholes`, независимо от того, какая
ветка `CASE` должна была сработать. Это воспроизведено в тесте на чистой
вставке в `boreholes` без каких-либо доработок с моей стороны — баг
исходного ТЗ, не привнесённый дополнением.
→ Функция переписана на `to_jsonb(NEW) ->> 'created_by'` и т.д. — доступ по
ключу jsonb безопасен для любой формы таблицы и просто возвращает `NULL`,
если колонки нет.

**1б. Триггер, запрещающий самоповышение роли, создаёт дедлок для первого
администратора.**
Первая версия `fn_prevent_self_role_change()` блокировала любое изменение
`role`, если `NOT is_admin()` — но `is_admin()` смотрит на `auth.uid()`,
который в контексте прямого SQL (Supabase SQL Editor, `service_role`,
сама эта миграция) равен `NULL`. Значит, назначить самого первого
администратора в свежей системе было невозможно ни через клиентский API
(ожидаемо), ни напрямую через Dashboard/SQL Editor (неожиданно и
блокирующе) — таблица `profiles` навсегда остаётся без единого админа.
→ Условие дополнено проверкой `auth.uid() IS NOT NULL` — блокировка
применяется только к запросам от имени конечного пользователя через REST
API (именно там и была исходная угроза из дополнения), а доверенный
серверный контекст без JWT может назначать роли свободно.

### Средней важности

**4. `SECURITY DEFINER`-функции без `SET search_path`.**
`is_admin()` в исходном виде — классический кейс подмены search_path
(если у атакующей роли есть право создавать объекты в схеме, идущей
раньше `public` в её search_path, можно подменить резолвинг имён внутри
функции). Это же поймает Supabase Database Linter
("Function Search Path Mutable").
→ Всем `SECURITY DEFINER`-функциям (`is_admin`, `fn_handle_new_user`,
`fn_prevent_self_role_change`, `fn_audit_changes`) добавлен
`SET search_path = public`.

**5. Нет RLS-политик на `storage.objects`.**
Раздел 5 ТЗ описывает бакеты только табличкой с текстом ("Авторизованные",
"Публичный") — это не RLS-политики. Без явных policy на
`storage.objects` (для приватных бакетов) авторизованный пользователь по
умолчанию не сможет вообще ничего (Supabase Storage по умолчанию deny),
либо, если кто-то по ошибке даст широкий policy — сможет читать/удалять
чужие файлы.
→ `002_storage_setup.sql`: политики под каждый бакет — `photos`/
`thumbnails` (читают/грузят все авторизованные, правит/удаляет только
владелец или админ), `tiles` (публичное чтение, пишет только админ),
`exports` (доступ только к папке `{user_id}/...`).

### Мелкие

**6. Дублирующийся индекс.**
`idx_boreholes_code (polygon_id, code)` в исходном ТЗ создаётся отдельно,
хотя `UNIQUE (polygon_id, code)` уже создаёт эквивалентный индекс —
лишний индекс только замедляет запись.
→ Убран, оставлен комментарий в миграции.

**7. `polygon_stats`: несогласованный подсчёт.**
`measurement_count` и `photo_count` не исключали записи, принадлежащие
уже мягко удалённым (`is_deleted = true`) скважинам/точкам наблюдений —
в отличие от `borehole_count`/`obs_point_count`, которые их исключают.
→ Подзапросы приведены к единому виду — учитывают `is_deleted` на всех
уровнях.

## Не тронуто (осознанно, вне рамок этой миграции)

- Отсутствие механизма очистки файлов в Storage при `is_deleted = true`
  или физическом удалении родителя — организационно решается на уровне
  API route/Edge Function на следующих этапах, не является багом схемы.
- `draft_code` / переименование при конфликте кода — логика на стороне
  клиента и `/api/sync`, будет реализована в Этапе 4 (офлайн).
